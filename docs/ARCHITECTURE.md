# معماری

اپ یک SPA از نوع React + TypeScript است که با Capacitor داخل یک WebView در Android اجرا می‌شود. همه‌چیز (کد، محتوا، فونت، تصاویر) داخل APK است.

## لایه‌ها

```
UI (pages، ui، games/*Card)         ← فقط از t()، stateها و repositoryها استفاده می‌کند
   │
state (zustand)                      ← حالت‌های UI و تنظیمات؛ منبع حقیقت = storage
   │
domain (توابع خالص)                  ← سطح/XP، شایستگی‌ها، (بعداً) امتیازدهی، Badge، Streak
games/<game>/engine (توابع خالص)     ← منطق هر بازی؛ بدون React و بدون storage
   │
storage/repositories                 ← تنها کدی که به جدول‌های Dexie دست می‌زند
   │
IndexedDB (Dexie)                    ← فقط روی دستگاه
```

قاعده‌ی وابستگی: `domain` و `games/*/engine` به React، Dexie یا Capacitor وابسته نیستند؛ فقط `platform/` افزونه‌های Capacitor را import می‌کند.

## ذخیره‌سازی

- جدول‌ها: `settings` (کلید-مقدار typed)، `profiles`، `attempts`، `questionStats`. Phase 2 جدول جدیدی نیاورد: مدال، Streak، چالش روزانه و رادار همه از `attempts` مشتق می‌شوند (فقط فیلدهای اختیاری تازه در `detail`: `misses`، `daily`، `dailyBonus` و `endedBy` گسترده‌تر). نسخه‌ی schema در `DB_SCHEMA_VERSION` و هر تغییر با `this.version(n)` جدید.
- **نسخه‌ی ۲ (Phase 1):** فیلد `experience` روی پروفایل (با migration که مقدار پیش‌فرض را برای ردیف‌های قدیمی پر می‌کند و تست می‌شود)، جدول `questionStats` با کلید مرکب `[profileId+questionId]`، و ایندکس `[profileId+contentId]` روی `attempts`.
- **`questionStats` یک cache قابل بازسازی است:** حالت Leitner هر سؤال، حاصل اجرای reducer روی پاسخ‌های ذخیره‌شده در `attempts.detail.answers` است. XP و سطح هرگز ذخیره نمی‌شوند؛ هر بار از جمع `attempts.xp` محاسبه می‌شوند (`useActiveXp()`).
- **ذخیره فقط در پایان دور:** `repos().rounds.record()` تلاش و به‌روزرسانی آمار سؤال‌ها را در یک تراکنش می‌نویسد (شکست = هیچ‌کدام نوشته نمی‌شود؛ تست شده). وسط دور هیچ نوشتنی نیست.
- **پیشرفت مشتق‌شده است:** `attempts` یک لاگ append-only از دورهای پایان‌یافته است و XP، سطح، Badge، آمار و رتبه‌بندی از روی آن محاسبه می‌شود. با این کار قوانین (توازن XP، شرط Badge) بدون migration داده قابل اصلاح است.
- چند پروفایل روی یک دستگاه (برای رتبه‌بندی محلی) از همان جدول `profiles` پشتیبانی می‌شود؛ `activeProfileId` در settings.
- **پشتیبان‌گیری:** یک فایل JSON با `format`، `formatVersion`، `DB_SCHEMA_VERSION`، نسخه‌ی برنامه و checksum (SHA-256) روی داده؛ جزئیات در بخش «Phase 3» پایین. `allowBackup` در Android عمداً خاموش است، پس انتقال داده فقط با همین قابلیت است.
- اگر IndexedDB در دسترس نباشد، برنامه با مقادیر پیش‌فرض کار می‌کند و `storageError` را در تنظیمات نشان می‌دهد.

## محتوا

- هر بازی بسته‌ی JSON خودش را دارد: `src/content/packs/<locale>/<نوع>.json`، با `schemaVersion` و `locale`.
- شناسه‌ی آیتم‌ها پایدار و مستقل از زبان است؛ بسته‌ی هر زبان باید زیرمجموعه‌ی شناسه‌های زبان پیش‌فرض باشد (تست می‌شود).
- اعتبارسنجی با zod فقط در تست (`npm test`) انجام می‌شود؛ zod در باندل نیست. loader فقط cast می‌کند، چون درستی بسته‌ها توسط تست تضمین می‌شود.
- هر آیتم `reviewStatus` دارد (`draft` یا `reviewed`). آیتم `reviewed` باید دست‌کم یک مرجع (استاندارد/بند) داشته باشد.
- بسته‌ها به‌صورت ماژول import می‌شوند (`import.meta.glob`)، نه `fetch`؛ چون اپ شبکه ندارد و CSP هم آن را نمی‌پذیرد.
- اگر زبانی بسته‌ی خودش را نداشته باشد، loader به زبان پیش‌فرض برمی‌گردد.

## i18n و افزودن انگلیسی

1. `src/i18n/messages/en.ts` بسازید و آن را به `Messages` مقید کنید (کلید کم یا اضافه خطای TypeScript می‌دهد).
2. در `locales.ts` متادیتا (`dir: 'ltr'`، `calendar: 'gregory'`، `intl: 'en-US'`) و در `i18n/index.ts` دیکشنری را ثبت کنید.
3. بسته‌های محتوا را در `src/content/packs/en/` بگذارید.
4. یک انتخابگر زبان در تنظیمات و ذخیره‌ی آن در `SettingsMap`؛ تغییر زبان = `applyLocale()` + reload.
5. فونت لاتین از قبل در باندل است. چند‌شکلی (plural) برای انگلیسی باید به `t()` اضافه شود (فارسی به آن نیاز ندارد).

CSS از ویژگی‌های logical (`inline-size`، `margin-inline-start`…) استفاده می‌کند، پس چیدمان در LTR هم درست می‌شود.

## تضمین‌های آفلاین (چند لایه)

| لایه | چه چیزی را می‌بندد | بررسی |
|---|---|---|
| Manifest بدون `INTERNET` | هیچ ارتباط شبکه‌ای از طرف سیستم‌عامل مجاز نیست | `verify:offline` |
| `allowBackup=false`، بدون cleartext | داده از طریق backup ابری Android خارج نمی‌شود | `verify:offline` |
| CSP در build | هیچ منبع/اتصال خارجی در WebView | `verify:offline --require-dist` + تست مرورگر |
| ESLint | `fetch`/`XMLHttpRequest`/`WebSocket`/`EventSource`/`sendBeacon` ممنوع | `npm run lint` |
| اسکن سورس | URL خارجی و API شبکه در کد/استایل/HTML | `verify:offline` |
| اسکن وابستگی‌ها | SDKهای بک‌اند، آنالیتیکس و crash-reporting | `verify:offline` |
| allowlist مجوز افزونه‌ها | Manifest هر افزونه‌ی Capacitor خوانده می‌شود؛ هر مجوزی جز چهار مورد مستند (VIBRATE، POST_NOTIFICATIONS، RECEIVE_BOOT_COMPLETED، WAKE_LOCK) رد می‌شود | `verify:offline` (با دست‌کاری عمدی آزموده شد) |
| ابزار توسعه در release | ویرایشگر مختصات نباید در `dist/` باشد | `verify:offline` |
| Manifest ادغام‌شده‌ی build واقعی | همان فهرست مجوزها (به‌علاوه‌ی مجوز امضایی خودِ androidx)، بدون `INTERNET`/وضعیت شبکه/آلارم دقیق، `allowBackup=false`، بدون cleartext، و در release بدون debuggable | `verify:merged` (پس از build؛ منطقش با تست و Manifest ساختگی آزموده شد) |

**محدودیت‌ها:** `verify:offline` Manifest خود اپ و Manifest هر افزونه را می‌خواند، ولی نه خروجی واقعیِ merge در Gradle را؛ آن را `verify:merged` بعد از اولین build واقعی می‌خواند (که در این محیط ممکن نیست: Android SDK نیست). حذف `SCHEDULE_EXACT_ALARM` با `tools:node="remove"` هم همان‌جا باید تأیید شود. اثبات این‌که WebView بدون `INTERNET` درست بالا می‌آید فقط با اجرا روی دستگاه ممکن است (نگاه کنید به ROADMAP).

## آزمون HSE (Phase 1)

**موتور خالص** (`games/quiz/engine.ts`، بدون React و storage):
- `prepareQuestion` سؤال را برای نمایش آماده می‌کند (shuffle با RNG قابل seed؛ ترتیب‌دهی و تطبیق هرگز «از قبل حل‌شده» نمایش داده نمی‌شوند). `isCorrect` پاسخ را برای ۴ نوع (چندگزینه‌ای، درست/غلط، تطبیق، ترتیب) می‌سنجد.
- `selectQuestions`: حالت موضوعی / ترکیبی / نقاط ضعف. سؤال‌های ندیده اول، بعد دیرترین موعد؛ تازه‌کارها سؤال سخت را فقط برای پر کردن دور می‌گیرند؛ دور از ساده به سخت مرتب می‌شود. بازیکن «عمومی» همه‌چیز می‌بیند، بازیکن یک صنعت = عمومی + صنعت خودش.
- ماشین‌حالت دور (`startRound` / `recordAnswer` / `summarizeRound`): سپر ۳ لایه، با هر پاسخ غلط یک لایه می‌شکند؛ صفر شدن لایه‌ها دور را زودتر تمام می‌کند (مگر آخرین سؤال بوده باشد).

**منطق مشترک** (`domain/`): `scoring.ts` (امتیاز هر سؤال، ستاره، XP دور)، `leitner.ts` (۵ جعبه با فاصله‌ی ۰/۱/۳/۷/۱۴ روز؛ پاسخ درستِ همراه با راهنما ارتقا نمی‌گیرد)، `levels.ts`، `stats.ts` (خلاصه‌ی پیشرفت از روی attempts). همه‌ی ثابت‌ها در همین فایل‌ها قابل تنظیم‌اند.

**رابط:** `QuizHub` (ترکیبی، مرور نقاط ضعف، ۱۳ موضوع) ← `QuizPlay` (بدون نوار پایین؛ لمس برای انتخاب سپس «ثبت پاسخ»؛ بازخورد با توضیح و مرجع) ← `QuizResult` (ستاره، تفکیک XP، ارتقای سطح، مرور اشتباه‌ها). خروج وسط دور (دکمه، برگشت مرورگر یا برگشت سخت‌افزاری Android) از طریق `useBlocker` تأیید می‌گیرد؛ به همین دلیل Router از نوع data router (`createHashRouter`) است.

**پروفایل:** بدون حساب کاربری؛ چند پروفایل محلی با نام مستعار یکتا، آواتار، صنعت و سطح تجربه. اگر پروفایلی نباشد (اولین اجرا یا حذف آخرین پروفایل) `Onboarding` سه‌مرحله‌ای جای برنامه را می‌گیرد و فقط در مرحله‌ی آخر ذخیره می‌کند.

## ماشین‌حالت دور مشترک و سه بازی (Phase 2)

`domain/round.ts` ماشین‌حالت یک دور را برای همه‌ی بازی‌ها نگه می‌دارد: فهرست آیتم‌ها به‌ترتیب بازی می‌شود، هر نتیجه امتیاز و «اعتبار» (credit بین ۰ و ۱) می‌گیرد، نتیجه‌ی ناموفق یک لایه‌ی سپر می‌شکند و دور با تمام شدن آیتم‌ها یا شکستن سپر تمام می‌شود. بازی‌ها فقط در معنای «آیتم» فرق دارند (سؤال، سناریو، خطر). `games/shared/finishRound.ts` تنها جایی است که یک دور ذخیره می‌شود: XP (شامل ضریب و پاداش روزانه)، تراکنش `rounds.record`، به‌روزرسانی Leitner (آزمون) و مدال‌های تازه.

**چالش ارزیابی ریسک** (`games/risk/`، `domain/risk.ts`): ماتریس ۵×۵ با باندهای ۱–۵/۶–۱۰/۱۱–۱۵/۱۶–۲۰/۲۱–۲۵. اعتبار ارزیابی از فاصله‌ی خانه‌ی بازیکن با خانه‌ی «کارشناس» (۱ / ۰٫۶ / ۰٫۲۵ / ۰)، اعتبار کنترل نسبت به گزینه‌های همان سناریو (بهترین ۱، دومی ۰٫۵)، وزن ۶۰/۴۰ و موفق = اعتبار ≥ ۰٫۵. سلسله‌مراتب: حذف > جایگزینی > مهندسی > اداری > PPE. ماتریس با شماره‌ی خانه و برچسب خوانا (نه رنگ تنها) رسم می‌شود.

**خطر را پیدا کن** (`games/hazard/`): هر دور یک صحنه است. نقطه‌ها دایره‌هایی در مختصات نرمال‌اند (`geometry.ts`: برخورد با نزدیک‌ترین مرکز، پذیرش تلرانس انگشت متناسب با زوم). لمس خالی یک لایه‌ی سپر می‌شکند، راهنما دایره‌ای بزرگ و عمداً خارج از مرکز می‌کشد (۱۵٪ امتیاز همان خطر؛ حداکثر ۳ بار). `PanZoomImage` با Pointer Events برای pinch، کشیدن و چرخ ماوس، با دکمه‌ها و کلید هم کار می‌کند و تفاوت «لمس» و «کشیدن» را می‌شناسد. خطرهای پیدا‌نشده با اعتبار ۰ ثبت می‌شوند تا آمار موضوع و رادار درست بماند. ابزار مختصات (`dev/HazardEditor`) فقط در dev ثبت می‌شود. جزئیات: `SCENES.md`.

**چالش مجوز کار** (`games/permit/`، `content/schema.ts`): هر مجوز یک فرم با بخش‌ها و خط‌هاست (`sections[].fields[]`) و `defects` کلید پاسخ است: هر خطا روی یک تا سه خط فرم می‌نشیند و لمس هرکدام از آن‌ها «پیدا شدن» حساب می‌شود؛ `critical` یعنی تأیید مجوز می‌تواند کشنده باشد. مجوز بدون خطا سالم است و باید تأیید شود (تصمیم درست از خود `defects` مشتق می‌شود، جدا ذخیره نمی‌شود). اعتبار: تصمیم ۴۰٪ + پیدا کردن خطاها ۶۰٪؛ هر خط اضافه‌ی علامت‌خورده ۳۰٪ از سهم خطاها کم می‌کند؛ با تصمیم غلط (یا بی‌تصمیمی با پایان زمان) فقط نصفِ سهم خطاها حساب می‌شود (تأیید مجوزِ خطادار حتی با همه‌ی خطاهای علامت‌خورده بدترین اشتباه است)؛ «موفق» = تصمیم درست + هیچ خطای بحرانی از قلم نیفتاده + اعتبار ≥ ۰٫۷. یک راهنما برای هر مجوز (تعداد خطاها، ۱۵٪ کمتر). `selectPermits` تضمین می‌کند دور فقط از مجوزهای معیوب نباشد (وگرنه «همه را رد کن» برنده می‌شد). علامت‌ها پیش‌نویس محلی‌اند و تنها «رد» یا «تأیید» آن‌ها را ثبت می‌کند.

**واکنش اضطراری** (`games/emergency/`): هر موقعیت ۳ تا ۵ مرحله دارد؛ هر مرحله ۳ یا ۴ اقدام با درجه‌ی `best` (دقیقاً یکی)، `acceptable` (امن ولی کم‌اثر) یا `harmful` (دست‌کم یکی) و متن «چه می‌شود». اعتبار موقعیت میانگین مرحله‌هاست (۱ / ۰٫۵ / ۰)؛ «موفق» = هیچ اقدام خطرناکی نباشد و میانگین ≥ ۰٫۷. داستان با فرض اقدام درست ادامه می‌یابد (و رابط این را می‌گوید)، پس پاسخ غلط مرحله‌های بعد را عوض نمی‌کند. ماشین‌حالت دور یک موقعیت را یک آیتم می‌بیند و بعد از مرحله‌ی آخر ثبتش می‌کند؛ در حالت زمان‌دار هر مرحله ۳۰ ثانیه دارد.

**چالش بو‌تای** (`games/bowtie/`): هر پاپیون یک خطر، یک رویداد اصلی و ۸ تا ۱۴ کارت دارد که هرکدام یکی از `threat`، `preventive`، `mitigating`، `consequence` یا `none` (مزاحم) است. بازیکن کارت را انتخاب می‌کند و بعد دکمه‌ی گروهش را می‌زند (بدون کشیدن‌ورها)؛ کارت چیده‌شده با لمس برمی‌گردد. اعتبار = سهم کارت‌هایی که در گروه درست‌اند؛ «موفق» از ۷۵٪. مانعی که سمت اشتباه رویداد اصلی رفته (پیشگیرانه ↔ کاهنده) جداگانه شمرده و در مرور گوشزد می‌شود، چون هدف اصلی بازی همین تمایز است.

**Streak و چالش روزانه** (`domain/streak.ts`، `domain/daily.ts`): Streak از روی روزهای تقویم محلی با حداقل یک دور محاسبه می‌شود و روزهای بعد از امروز را نمی‌شمارد، پس جلو بردن ساعت چیزی نمی‌سازد (عقب بردن می‌تواند روزی را پر کند؛ نگاه کنید به DECISIONS). چالش روزانه سه مأموریت وابسته‌ی فقط به تاریخ است (موضوع آزمون از یک چرخه‌ی ۱۵روزه‌ی ثابت، یک دور ریسک، یک صحنه). مأموریت وقتی حساب می‌شود که از صفحه‌ی روزانه شروع شده (`?daily=1`)، کامل شده و آن روز هنوز شمرده نشده باشد؛ اولین دور XP دوبرابر می‌دهد و تکمیل هر سه ۱۰۰ XP اضافه. `finishRound` تصمیم می‌گیرد؛ پرچم URL به‌تنهایی کافی نیست.

**مدال‌ها و رادار** (`domain/badges.ts`، `domain/radar.ts`، `progress/`): یازده مدال سه‌سطحی (هر بازی یکی دارد) (برنزی/نقره‌ای/طلایی) که هر کدام یک معیار روی `attempts` است؛ تفاوت وضعیت قبل و بعد از دور «مدال تازه» را در صفحه‌ی نتیجه می‌سازد. رادار شش محور دارد (ایمنی، ارزیابی ریسک، مدیریت بحران، قوانین، محیط زیست، بهداشت حرفه‌ای؛ هر موضوع از طریق `TOPIC_DOMAIN` دقیقاً به یک محور وصل است و جدول کامل‌بودن آن را کامپایلر تضمین می‌کند). مقدار هر محور میانگین اعتبار آخرین ۳۰ پاسخ است و زیر ۳ پاسخ «داده‌ی کافی نیست» نشان داده می‌شود. نمودار یک تصویر برچسب‌دار است و همان اعداد در جدول کنارش (جایگزین قابل‌دسترس) هستند؛ tooltip فقط تکمیل است. «پیشنهاد ویژه» اول محوری را می‌گوید که داده ندارد، بعد ضعیف‌ترین.

## رتبه‌بندی، پشتیبان‌گیری، یادآور، صدا و لرزش (Phase 3)

**رتبه‌بندی محلی** (`domain/leaderboard.ts`، تب «رتبه‌بندی» در پیشرفت): پروفایل‌های همین دستگاه بر پایه‌ی XP، برای «کل زمان» و «۷ روز اخیر». از `attempts` هر پروفایل مشتق می‌شود و جدول جدیدی ندارد؛ برابری رتبه مشترک است (۱، ۱، ۳) و پروفایل بی‌امتیاز رتبه ندارد. دورهای با تاریخ بعد از امروز (ساعت جلو رفته) در هفته شمرده نمی‌شوند.

**پشتیبان‌گیری** (`storage/backup.ts`، `backup/`): فایل JSON شامل پروفایل‌ها، لاگ کامل `attempts` و cache تکرار فاصله‌دار. checksum خرابی و ویرایش دستی را می‌گیرد و امضا نیست (پیشرفت محلی است و رقابتی نیست). **ورودی فقط «ادغام» است:** `planMerge` که تابعی خالص است، شناسه‌های موجود را رد می‌کند، نام تکراری را عوض می‌کند (`علی (2)`) و چیزی را جایگزین یا حذف نمی‌کند؛ `applyMerge` همه را در یک تراکنش می‌نویسد (شکست = هیچ‌چیز نوشته نمی‌شود؛ تست شده). فایل پیش از هر نوشتن اعتبارسنجی می‌شود: JSON، `format`، نسخه‌ی جدیدتر، checksum، شکل هر ردیف، یکتایی شناسه‌ها و ارجاع هر دور به یک پروفایل موجود در همان فایل؛ اعتبارسنجی دست‌نویس است چون zod در باندل نیست. در Android فایل در cache خصوصی برنامه نوشته و با Share باز می‌شود (بدون مجوز ذخیره‌سازی)؛ در مرورگر دانلود ساده است. بازیابی هم در تنظیمات هست و هم در صفحه‌ی خوش‌آمد اجرای اول (حالت «گوشی تازه»)، و همیشه بعد از نمایش محتوای فایل و تأیید کاربر.

**یادآور روزانه** (`domain/reminder.ts`، `reminders/`، `platform/reminders.ts`): پیش‌فرض خاموش و فقط در برنامه‌ی Android. چون برنامه آفلاین است و هنگام اعلان کدی اجرا نمی‌شود، به‌جای یک اعلان تکرارشونده ۷ روز آینده زمان‌بندی می‌شود و در شروع برنامه، بازگشت از پس‌زمینه، پایان هر دور و هر تغییر تنظیم دوباره چیده می‌شود. اگر امروز بازی شده باشد اعلان امروز حذف می‌شود. اعلان غیردقیق است (نیازی به `SCHEDULE_EXACT_ALARM` نیست) و اجازه‌ی `POST_NOTIFICATIONS` فقط هنگام روشن‌کردن یادآور پرسیده می‌شود.

**صدا و لرزش** (`feedback/`): بازی‌ها فقط `feedback(kind)` را صدا می‌زنند. صدا با WebAudio ساخته می‌شود (بدون فایل صوتی؛ هر افکت چند نت کوتاه با بلندی کم، تست‌شده برای محدوده و طول) و پیش‌فرض **خاموش** است؛ لرزش با Haptics پیش‌فرض **روشن**. پیش از اولین لمس کاربر هیچ AudioContext ساخته نمی‌شود (هشدار autoplay نمی‌دهد).

**انیمیشن‌ها:** شکستن لایه‌ی سپر (ترک و فلش قرمز)، ستاره‌ها و کارت ارتقای سطح، مدال تازه، حلقه‌ی خطر پیداشده و کارت بازخورد. همه با یک قاعده‌ی سراسری `prefers-reduced-motion` در `ui/global.css` خنثی می‌شوند (E2E مدت واقعی انیمیشن را در هر دو حالت می‌خواند).

## سرعت، دسترس‌پذیری و انتشار (Phase 4)

**بارگذاری تنبل:** فقط پوسته و صفحه‌ی خانه در باندل اولیه‌اند؛ هر صفحه و هر بازی (و بسته‌ی محتوایش) در chunk جدا می‌آید (`app/router.tsx`، `lazy`). chunkها فایل محلی‌اند و آفلاین کار می‌کنند؛ router تا رسیدن chunk صفحه‌ی قبل را نگه می‌دارد، پس پرش سفید نیست (و نوار نازک بالا فقط اگر بیش از ۱۵۰ms طول بکشد دیده می‌شود). `npm run perf` همین را با CPU کندشده می‌سنجد.

**تایمر و پس‌زمینه:** `games/shared/stopwatch.ts` (تابع خالص، ساعت از بیرون می‌آید) زمانی را که برنامه در پس‌زمینه بود نمی‌شمارد؛ `useQuestionTimer` آن را به `onAppActiveChange` (Android `appStateChange` یا `visibilitychange` وب) وصل می‌کند. هم شمارنده‌ی زمان‌دار و هم امتیاز سرعت از همین ساعت می‌آیند.

**دسترس‌پذیری:** هر صفحه یک `main` و (در بازی‌ها برای صفحه‌خوان) یک `h1` مخفی دارد (`.sr-only` در `ui/global.css`)؛ radiogroupها `div`اند نه فهرست؛ حالتی که فقط با کم‌رنگی بیان می‌شد (سطح کنترل ارائه‌نشده در سناریو) حالا خط‌چین است و متنِ صفحه‌خوان دارد؛ ریشه‌ی هر صفحه‌ی grid با `minmax(0, 1fr)` می‌تواند در متن بزرگ جمع شود. **خطر را پیدا کن بدون لمس تصویر:** `geometry.ts` دو تابع خالص دارد (`moveCursor`، `followCursor`)؛ `PanZoomImage` نشانه‌ی هدف را (در لایه‌ی زوم‌شده، با اندازه‌ی ثابت از طریق `--zoom`) با کلیدهای جهت‌دار یا فلش‌های صفحه جابه‌جا می‌کند، تصویر دنبالش می‌آید و Enter یا «ثبت» همان‌جا را می‌زند. E2E با axe-core و اندازه‌گیری هدف لمسی روی هر صفحه‌ای که عکس می‌گیرد اجرا می‌شود.

**انتشار:** `package.json` تنها منبع نسخه است (`scripts/sync-version.mjs`، `versionCode` = `x*10000 + y*100 + z`)؛ امضای release از متغیر `HSEQUEST_KEYSTORE_PROPERTIES` می‌خواند و بدون آن release بدون امضا ساخته می‌شود. آیکون و Splash و favicon و تصویرهای لوگوی داخل اپ (`src/assets/brand/`: نشان برای سربرگ خانه، کل لوگو برای صفحه‌ی خوش‌آمد) با `npm run assets:android` از لوگوی `branding/logo.svg` ساخته می‌شوند (Chromium): آیکون و favicon و سربرگ فقط نشان، Splash و صفحه‌ی خوش‌آمد کل لوگو. فایل SVG (۷۹۰KB) داخل اپ بسته‌بندی نمی‌شود. `scripts/permissions.mjs` فهرست مجوزهای مجاز است که هم `verify:offline` و هم `verify:merged` از آن می‌خوانند.

**محتوا و بازبینی:** هر آیتم محتوا `reviewStatus` دارد؛ `reviewed` یعنی `review: { by, at }` (نام و تاریخ بازبین) و دست‌کم یک مرجع هم دارد (schema اجبار می‌کند، و `draft` نمی‌تواند `review` داشته باشد). `scripts/content-review.mjs` برگه‌ی CSV می‌سازد و نتیجه را می‌پذیرد (فقط با `--write` می‌نویسد؛ تأیید آیتم بدون مرجع را رد می‌کند)، `scripts/verify-release.mjs` تا هر آیتم `draft` است build نهایی را رد می‌کند، و ثابت `__CONTENT_UNREVIEWED__` (زمان build از همان بسته‌ها) باعث می‌شود «درباره» به بازیکن بگوید بخشی از محتوا بازبینی نشده.

## تست

- Vitest در محیط node ({TESTS} تست): منحنی سطح/XP، امتیازدهی و ستاره، Leitner، RNG، موتور آزمون (آماده‌سازی، انتخاب، ماشین‌حالت، آمار)، آمار پیشرفت، اعتبار نام مستعار، i18n (ارقام و تاریخ جلالی)، schema و کل بانک‌های محتوا (سؤال، سناریو، صحنه)، اندازه‌ی واقعی تصویر صحنه‌ها، contrast رنگ‌های طراحی (WCAG AA)، ماشین‌حالت دور، ماتریس ریسک، هندسه و موتور خطر، Streak، چالش روزانه، مدال‌ها، رادار، رتبه‌بندی، برنامه‌ریزی یادآور و سرویسش (با mock افزونه)، صدا، فرمت/اعتبارسنجی/ادغام پشتیبان با repositoryهای واقعی با `fake-indexeddb` (شامل migration از v1 و برگشت تراکنش)، ساعت توقف‌پذیر تایمر، هندسه‌ی نشانه‌ی هدف، و اسکریپت‌های انتشار (Manifest ادغام‌شده، نسخه، CSV و حلقه‌ی بازبینی).
- **قرارداد محتوا:** loader فقط cast می‌کند، پس schema هیچ مقدار پیش‌فرضی ندارد و تستی ثابت می‌کند `parse(pack)` با JSON خام برابر است. (در Phase 1 همین تله یک crash واقعی ساخته بود: تست‌های واحد از zod عبور می‌کردند و پیش‌فرض‌ها را می‌دیدند، ولی اپ JSON خام را.)
- هر موتور بازی به‌صورت تابع خالص نوشته می‌شود و تست واحد دارد؛ برای چالش روزانه از RNG با seed تاریخ استفاده خواهد شد.
- **E2E (`npm run e2e`، {E2E} بررسی؛ در Phase 4 این‌ها اضافه شد: axe-core و هدف لمسی روی ۵۲ صفحه/حالت، تم روشن، متن ۱۳۰٪/۲۰۰٪، توقف تایمر در پس‌زمینه، جایگاه در مرور ترتیب، کنترل «خطر را پیدا کن» با کیبورد و دکمه، و اعلان محتوای بازبینی‌نشده):** build production را در Chromium واقعی اجرا می‌کند و مثل کاربر بازی می‌کند: Onboarding، هر ۴ نوع سؤال، شکست سپر، مرور نقاط ضعف، تأیید خروج، چالش ریسک (ماتریس، کنترل، اعتبار جزئی)، خطر را پیدا کن (لمس، راهنما، زوم و کشیدن، تمام‌کردن، شکست سپر، انصراف)، چالش روزانه کامل با ضریب دو و پاداش ۱۰۰، مدال‌ها و رادار و تب‌های پیشرفت، چند پروفایل، حالت زمان‌دار، رتبه‌بندی با یک و دو پروفایل، ساخت و دانلود فایل پشتیبان و بازیابی آن (فایل خراب، دست‌کاری‌شده، از نسخه‌ی جدیدتر، ناسازگار؛ فایل دستگاه دیگر با تغییر نام؛ و «گوشی تازه» با حذف پروفایل و بازیابی از صفحه‌ی خوش‌آمد)، تنظیمات صدا و لرزش با شمارش واقعی oscillatorها و `navigator.vibrate` (روشن، خاموش، ماندگاری)، انیمیشن‌ها در حالت عادی و کاهش حرکت، ماندگاری بعد از reload، نبودن ابزار dev در build، صفر درخواست خارجی و صفر خطا/هشدار کنسول. عمداً بخشی از `npm run check` نیست چون کند است و Chromium می‌خواهد. در Phase 2 هم چند باگ واقعی را همین E2E پیدا کرد: دکمه‌های زوم روی خطرها می‌افتادند (حالا زیر تصویرند)، tooltip رادار در RTL جابه‌جا بود، و hit targetِ محورهای بدون داده روی هم می‌افتاد.
